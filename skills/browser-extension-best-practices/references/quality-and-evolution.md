# 质量、版本发布与配置演进

按 [优化流程](guide.md) 确定范围。推荐 Changesets 管理发布意图和产品版本；发布版本、配置 Schema 与数据库版本分别维护。

## 工程质量

项目脚本是本地和 CI 的检查入口。保留已工作的 Lint、格式化与测试工具；缺少行为测试时推荐 Vitest，已有 Node test runner 等能够验证风险时继续使用。Hooks 提供本地反馈，必要检查仍由 CI 执行。

| 层级 | 重点 | 完成证据 |
| --- | --- | --- |
| 静态检查 | 类型、格式、Lint、翻译键与依赖边界 | 与 CI 相同命令及实际结果 |
| 行为测试 | 业务规则、消息校验、竞争顺序、历史配置、失败恢复 | 代表性输入和断言；异步交错用可控 Promise/时钟 |
| 构建产物 | manifest、权限、入口、语言资源、图标、编译后的后台协议 | 检查生成目录及最终 ZIP 内容 |
| 浏览器验收 | 安装/更新、真实入口、iframe、宿主样式、权限、worker 生命周期 | 明确浏览器、版本、产物和复现场景 |

对已发生或高风险的缺陷增加最小回归。DOM 模拟器或 VM 可运行编译后的后台，验证消息保持通道、路由和失败后顺序；它们不能证明浏览器权限、隔离世界或 worker 真实生命周期。外部网络测试与确定性回归分开，跳过外部测试时单独报告。

产物检查围绕产品契约：校验 manifest 版本和权限预期、入口文件存在、默认 locale 与支持语言、图片实际尺寸；定位最终提交 ZIP 中的同一内容。若打包命令重新构建，必须检查最终包，不能只验证上一次构建目录。Firefox 需要源码包时，验证解压后可按说明重建且没有混入密钥。[WXT 打包与发布](https://wxt.dev/guide/essentials/publishing)

## Changesets

**默认推荐 `@changesets/cli`。** 单个扩展以一个产品版本聚合变更；独立发布的扩展、网站或公共库分别确定发布单元。仅确有版本联动需求时使用 fixed/linked 策略。已有工具提供变更意图、版本审阅和产物追踪时可保留。

用项目包管理器初始化 Changesets，配置实际基准分支及包名。私有扩展包如需版本更新，显式检查 `privatePackages.version`；tag 由 Changesets 或自定义发布流程中的一方负责，避免重复创建。私有包策略以安装版本的 [Changesets 配置](https://changesets.dev/guide/config) 为准。

默认版本语义：修复和兼容性维护为 patch，向后兼容的新功能为 minor，需要用户或消费者适应的不兼容变化为 major。已有产品政策可细化，但须明确；提交类型 `feat` 本身不能代替版本判断。配置 Schema 升级另行决策。

用户可见的变更附带 changeset，例如：

```markdown
---
"my-extension": patch
---

修复快速连续调整设置时较早结果覆盖较新输入的问题。
```

`my-extension` 替换为真实 package name。纯文档或开发工具改动按实际发布影响判断；免发布通过空 changeset 或明确的免发布标记记录理由。

**PR 检查：** 用 `changeset status --since=<base-ref>` 等已安装版本支持的命令校验记录，并确保基准 ref 已获取。另验证当前 PR 对用户有影响的包是否有记录，或有可解释的免发布理由；“仓库已有待发布 changeset”不足以证明当前 PR 已覆盖。版本 PR 单独识别，避免要求它再生成 changeset。[Changesets CLI](https://changesets.dev/guide/cli)

**最小接入验收：** 在临时分支或副本中用一条 patch 和一条 minor 验证预期版本、日志与记录消费；检查私有包、免发布和遗漏记录场景。检查命令通过后再接自动发布。

## 完整发布流程

推荐链路：业务 changeset → 版本 PR → 审阅合并 → 固定提交构建验证 → 打包 → 带完整附件的 GitHub Release → 商店提交 → 审核与公开状态确认。

| 阶段 | 实施要求 | 完成条件 |
| --- | --- | --- |
| 1. 归集变更 | 自动在主分支更新后或手动触发版本 PR，沿用产品发布节奏 | 待发布变更属于明确的发布单元 |
| 2. 生成版本 PR | Changesets 更新版本和 CHANGELOG、消费记录；使用同一版本来源生成 manifest | 差异包含预期版本、日志、必要锁文件，原 CI 继续通过 |
| 3. 审阅合并 | 审查升级级别、用户说明、权限与数据变化；只对可信版本 PR 或指定发布提交触发后续 | 发布 commit SHA 固定，不受之后 main 前进影响 |
| 4. 构建验证 | 干净检出该 SHA，锁定依赖安装，运行相关检查与目标浏览器构建 | 所有发布目标有对应检查结果 |
| 5. 打包核验 | 明确指定预期 ZIP，解压检查版本、入口和资源，记录 SHA 与校验和 | 包内容对应验证结果；源码包按渠道要求可重建 |
| 6. 发布 Release | 校验 tag 指向该 SHA，附对应版本说明和全部预期附件；可先建草稿，完整后公开 | Release、tag、版本、附件与校验和一致 |
| 7. 提交商店 | 使用已验证的同一 ZIP，按现有授权及渠道配置提交 | 记录渠道、扩展 ID、版本及提交结果 |
| 8. 核对分发 | 从商店后台确认审核状态；发布后检查对应渠道公开入口或更新分发 | 分别报告已上传、待审核、已批准、已公开及适用范围 |

推荐 `changesets/action` 管理版本 PR，扩展产物由专门脚本或 job 发布，避免把扩展误当作 npm 包。实现时核对 Action 与 CLI 主版本兼容性、输入名称和 tag/Release 所有者；如果由自定义流程发布，关闭 Action 重复创建这些对象的行为。[Changesets Action](https://github.com/changesets/action)

CI 权限按任务分配：PR 检查使用只读权限，版本 PR 所需写权限仅给可信 job，商店凭据仅给提交阶段。明确工作流触发链；使用默认 GitHub token 创建的 PR/提交可能不会触发期望的后续工作流，核对平台限制并验证检查确实运行，按需选择 GitHub App token 或受控显式触发。[GitHub 工作流触发规则](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow)

首次上架先完成开发者账户、listing、权限说明、隐私政策和渠道所需素材。WXT 的 `wxt submit` 可提交已有扩展更新；凭据与 dry run 按官方文档配置，命令成功或 dry run 通过不等于商店审核通过。已有持续发布授权时按其执行，范围只含流程配置时停在本地验证。

### 重试与恢复

| 失败位置 | 恢复方式 |
| --- | --- |
| 检查或构建失败 | 停止公开发布，修复后重新验证确定的提交 |
| tag 已存在 | 对照本地与远端实际提交；一致才继续，不一致停止并报告冲突 |
| Release 已存在但附件不全 | 核验版本、提交及已有附件，补齐缺失产物；仅存在 Release 不能判为完成 |
| 同名附件内容不同 | 停止覆盖，调查构建输入或版本归属；修复版本按发布政策处理 |
| 部分商店提交成功 | 记录各渠道状态，仅重试未完成渠道，复用相同已验证产物 |
| 发布后发现缺陷 | 按渠道能力停止分发或发布修复版本；通常不能靠移动 tag 或上传较低版本回滚 |

发布流程按发布单元串行，避免取消正在上传的任务。认证失败或网络错误应报告为查询失败，不能被当成“tag/Release 不存在”。再次运行应识别已完成阶段并校验其内容，而非盲目重做。恢复需额外权限或会覆盖已公开内容时，停在可审阅的状态说明问题。

**流程验收：** 在隔离环境或 mock API 中覆盖 tag 已存在、附件缺失、构建失败与部分渠道失败。实际发布后另核对 GitHub 和商店证据。实现发布文档或脚本本身不授权执行外部发布。

## 配置升级

删除内部兼容代码与保护已发布用户数据分别判断。先列出稳定设置、用户内容、可重建缓存及临时状态；只有已明确允许丢弃的数据才采用失效重建。存储 key 更名也可能让旧数据失联，需要迁移、显式重置契约或保留 key。

**默认推荐：** WXT 设置演进优先使用 `storage.defineItem` 的 `version` 与 `migrations`；已有迁移机制继续使用。复杂导入、同步或数据库演进再评估独立迁移模块。类型声明、fallback 和 normalize 不等于历史数据兼容。[WXT 版本化存储](https://wxt.dev/storage.html#versioning)

1. **定义历史。** 发布版本、配置 Schema、数据库版本分开，列出启动、导入、恢复、同步入口；无版本数据按真实历史解释。完成条件：旧数据有唯一解释，不支持的未来版本被拒绝或保留，不能覆盖为默认值。
2. **转换与校验。** 从保留的原始值生成候选值，每步固定历史默认值，保留用户显式选择，最终校验当前格式。完成条件：缺步和失败可检测，失败步骤不会标为成功；同一历史样本不随新业务常量改变结果。
3. **提交与恢复。** 依据存储能力选择事务、备份或临时槽位，协调数据与版本；检查库实际提交语义，多次写入不自动构成事务。完成条件：中断后可识别状态并安全重试，失败仍可恢复原数据。
4. **控制消费者。** 初始化完成后再允许依赖新格式的读写，所有入口采用一致错误契约。完成条件：首次读取或后台唤醒不会提前覆盖历史设置。
5. **验证历史样本。** 覆盖最旧支持版本到当前、已有值保留、重复执行、未来版本、损坏输入和写入中断。完成条件：验证数据与版本都正确，且恢复路径实际可用。

简单的向后兼容加字段可以沿用稳定默认值补齐；需要区分“缺失”与“用户选择”时保留原始信息到迁移完成。只在真实数据变化需要时增加迁移，避免为每次产品发版创建空迁移。
